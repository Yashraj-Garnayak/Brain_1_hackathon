# TILE RUSH — Cloudflare Worker + Durable Objects

Realtime edge layer for TILE RUSH, ready for 1v1. The REST API keeps running on
Vercel/Neon during the migration; this Worker serves the static client, proxies
`/api/*` to the current API origin, and owns matchmaking and match rooms.

## What is here

| File | Purpose |
| --- | --- |
| `wrangler.toml` | Worker config, assets binding, DO bindings + migration |
| `src/index.js` | Router: health, queue, match socket, API proxy, static assets |
| `src/queue-room.js` | Global matchmaking queue (pairs two names, returns a match id) |
| `src/match-room.js` | Hibernating WebSocket Durable Object for one 1v1 match |
| `public/` | Generated by `npm run worker:assets` — never commit it |

## Run locally

From the repo root:

```bash
npm install
npm run worker:assets        # copies index.html, css/, js/, shared/ into worker/public
npm run worker:dev           # wrangler dev on http://localhost:8787
```

`worker:assets` exists so Wrangler uploads only the site. Do not point the assets
directory at the repo root; `.env.local` lives there.

## Deploy

The **Workers Free plan is enough**. Durable Objects with the SQLite backend
(what `wrangler.toml` already declares via `new_sqlite_classes`) are available
on free, and static assets are not counted against the Worker request quota.

```bash
npx wrangler login           # free Cloudflare account, one time
npm run worker:check         # dry-run bundle, validates config + DO classes
npm run worker:deploy        # creates https://<worker>.<subdomain>.workers.dev
```

Free-tier limits that matter here:

| Resource | Free allowance | What it means for TILE RUSH |
| --- | --- | --- |
| Worker requests | 100,000 / day | API proxy + queue polls; static files are free |
| Worker CPU | 10 ms / invocation | the router and DO handlers are far below this |
| DO requests | 100,000 / day | incoming WebSocket messages bill at 20:1 |
| DO duration | 13,000 GB-s / day | hibernation makes idle matches free |
| SQLite rows | 5M read / 100k written per day | writes happen on join/ready/finish, not progress |
| DO storage | 1 GB per object, 5 GB total | match state is a few KB |

A 60-second match with two players costs roughly 150 WebSocket messages and
about 8 GB-s of active time, so one free account covers hundreds of matches a
day. Exceeding a free limit fails the operation; it never produces a bill.

`uday.live` is on Vercel DNS, not Cloudflare, so attach a `workers.dev` hostname
rather than a subdomain of `uday.live`. Keep the REST API on Vercel, mint a
short-lived signed match ticket there (`POST /api/match/ticket`) and pass it to
the Worker — cookies cannot cross to a different hostname.

The Worker is stateless for accounts; sessions and runs still live in Neon until
phase 2. `API_ORIGIN` in `wrangler.toml` points at the current Vercel
deployment; update it if the domain changes.

## Realtime protocol

Matchmaking is a poll, not a socket:

```
POST /api/match/queue?name=uday
  -> { waiting: true, position: 1 }
  -> { matchId: "…", waiting: false }          # after the second player joins
```

Then both players open `GET /api/match/:id/ws` and speak JSON:

| Client → server | Server → client |
| --- | --- |
| `{ type: 'join', player: { name, avatar? } }` | `{ type: 'state', you, match }` |
| `{ type: 'ready', ready: true }` | `{ type: 'peer', player }` |
| `{ type: 'progress', round, correct, score }` | `{ type: 'countdown', round, startsAt }` |
| `{ type: 'finish', score, bpi }` | `{ type: 'progress', from, round, correct, score }` |
| `{ type: 'emote', id }` | `{ type: 'emote', from, id }` |
| `{ type: 'rematch' }` | `{ type: 'result', winner, players }` |
| `{ type: 'ping' }` | `{ type: 'pong', now }` |

Allowed emotes: `gg`, `wave`, `nice`, `oops`, `focus`, `rematch`.

The room starts a 3-second countdown once both players send `ready`. Scores are
clamped, messages are capped at 4 KB, and only whitelisted emotes are relayed.

## Security before launch

The room currently trusts the name a client sends. Before 1v1 ships:

1. Verify the `tr_session` cookie (or a one-time match ticket minted by
   `/api/runs`) before `join`, and bind the socket to the authenticated user id.
2. Never accept a client-supplied score as final; replay the run server-side or
   verify a signed run token.
3. Rate-limit queue joins per user and add a matchmaking cooldown.
4. Add a turn/clock authority in the room so a client cannot stretch a break.

## 1v1 design once this is live

The solo format (3×3 / 25 s, 4×4 / 15 s, 5×5 / 10 s, 5-second breaks) maps
directly onto a duel: the same seed deals the same targets to both players, each
plays their own board, and the room compares score at the end of each round.
Emotes ride the existing breaks. The rating delta can reuse `lib/elo.js` with a
head-to-head expected score instead of the solo baseline.
